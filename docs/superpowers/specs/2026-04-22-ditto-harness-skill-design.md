# Ditto Long-Running Harness Skill — Design Spec

> **Date:** 2026-04-22
> **Status:** Design Approved
> **PRD Reference:** `doc/PRD.md`
> **Inspiration:** Anthropic Engineering Blog — [Effective Harnesses for Long-Running Agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Harness Design for Long-Running App Development](https://www.anthropic.com/engineering/harness-design-long-running-apps), [Managed Agents](https://www.anthropic.com/engineering/managed-agents)

## 1. Overview

A Claude Code skill (`/ditto-implement`) that drives long-running, TDD-based implementation of the Ditto desktop pet project. The skill follows Anthropic's harness pattern: initializer agent sets up phase artifacts, coder agent implements one feature at a time, and evaluator agent gates quality at phase boundaries.

**Design decisions:**
- One skill covering all 5 PRD phases — phase detection is dynamic
- Per-phase initialization — feature lists generated from PRD + current codebase state
- TDD enforcement — red-green-refactor cycle per feature
- Evaluator gate between phases — code-reviewer subagent grades work
- Testing: Rust `cargo test` for backend, Playwright MCP for visual frontend verification

## 2. Harness Artifacts

### 2.1 File Structure

```
ditto-harness/
├── ditto-progress.json          # Master progress: current phase, overall status
├── phase-1/
│   ├── feature-list.json        # Phase-specific features (generated by initializer)
│   ├── phase-config.json        # Phase metadata: init/test/build commands
│   └── phase-eval-report.md     # Evaluator's final report for this phase
├── phase-2/
│   └── ...
├── phase-3/
│   └── ...
├── phase-4/
│   └── ...
└── phase-5/
    └── ...
```

### 2.2 ditto-progress.json

Master state file. Single source of truth for harness progress.

```json
{
  "current_phase": 1,
  "phase_status": {
    "1": "in_progress",
    "2": "pending",
    "3": "pending",
    "4": "pending",
    "5": "pending"
  },
  "total_features_completed": 0,
  "total_features_remaining": 0,
  "last_session_summary": "",
  "last_commit": ""
}
```

### 2.3 phase-N/feature-list.json

Generated at phase start from PRD verification checklists and current codebase state.

```json
[
  {
    "id": "P1-001",
    "description": "Pet appears on desktop with transparent background",
    "category": "functional",
    "test_type": "visual",
    "steps": [
      "Run `cargo tauri dev`",
      "Verify window has no visible background",
      "Verify pet sprites render correctly"
    ],
    "passes": false,
    "commit": null
  }
]
```

**Fields:**
- `id` — `P{N}-{SEQ:03d}` format (e.g., `P1-001`, `P2-007`)
- `test_type` — one of: `"unit"` (cargo test), `"visual"` (Playwright), `"integration"` (multi-component test with external dependencies), `"manual"` (user verification), `"profiling"` (performance measurement)
- `passes` — only field that may be changed after creation (false → true)
- `commit` — hash of the commit that marked this feature as passing

**Invariant:** Features must never be removed, reordered, or have their descriptions/steps modified. Only `passes` and `commit` fields may change.

### 2.4 phase-N/phase-config.json

Per-phase execution context.

```json
{
  "init_command": "cargo tauri dev",
  "test_command": "cargo test",
  "build_command": "cargo build",
  "playwright_checks": true,
  "phase_gate_criteria": [
    "All features pass",
    "Zero cargo test failures",
    "Evaluator review approved"
  ]
}
```

## 3. Harness Loop

### 3.1 Session Start — Get Bearings

Every invocation of `/ditto-implement` starts with this sequence:

```
1. pwd → confirm working directory
2. Read ditto-harness/ditto-progress.json → current phase & status
3. Read ditto-harness/phase-N/feature-list.json → remaining features
4. Run git log --oneline -20 → recent history
5. Run cargo test → baseline health check
6. Proceed to appropriate branch
```

### 3.2 Branch A — Phase Not Yet Initialized

Triggered when `phase-N/` directory does not exist for the current phase.

```
1. Read doc/PRD.md → extract Phase N requirements and verification checklist
2. Read current codebase state (Cargo.toml, src-tauri/, src/, assets/)
3. Run cargo test if Cargo.toml exists → record baseline test count
4. Generate phase-N/feature-list.json:
   - Map each PRD verification checklist item to a feature entry
   - Assign test_type based on feature nature
   - Assign id as P{N}-{SEQ:03d}
   - Order by dependency (foundational features first)
5. Generate phase-N/phase-config.json with init/test/build commands
6. Update ditto-progress.json: set phase status to "in_progress"
7. Git commit: "harness: initialize phase N feature list (X features)"
```

### 3.3 Branch B — Phase In Progress

Triggered when phase is "in_progress" and features remain with `passes: false`.

```
1. Find first feature with "passes": false
2. TDD Cycle (see Section 4)
3. If feature passes → mark feature "passes": true, record commit hash
4. Git commit
5. Update ditto-progress.json with completion stats
6. Repeat from step 1 if context allows
```

### 3.4 Branch C — Phase Gate

Triggered when all features in current phase have `passes: true`.

```
1. Spawn code-reviewer subagent as evaluator (see Section 5)
2. If evaluator approves:
   - Write phase-N/phase-eval-report.md
   - Update ditto-progress.json: phase status → "completed", advance current_phase
   - Git commit: "harness: phase N complete — evaluator approved"
   - Output summary to user
3. If evaluator rejects:
   - Add issues as new features to feature-list.json with "passes": false
   - Return to Branch B to fix
```

### 3.5 Session End — Clean State

Every invocation ends with:

```
1. Ensure all changes are committed
2. Update ditto-progress.json last_session_summary and last_commit
3. Report progress: "Phase N: X/Y features complete. Next: [feature id]"
```

## 4. TDD Enforcement — Red-Green-Refactor

Each feature follows this strict sequence. The skill enforces it by verifying each step completes before proceeding.

### 4.1 Red Phase — Write Failing Test

```
1. Write a test for the feature:
   - "unit" → write #[test] fn in appropriate Rust module
   - "visual" → write Playwright test spec
2. Run the test → confirm it FAILS
3. If test doesn't fail, the test is wrong — rewrite it
4. Git commit: "test: [feature id] — failing test for [description]"
```

### 4.2 Green Phase — Make It Pass

```
5. Write minimum code to make the test pass
6. Run the test → confirm it PASSES
7. Run cargo test (full suite) → confirm no regressions
8. If other tests break, fix them before proceeding
9. Git commit: "feat: [feature id] — implement [description]"
```

### 4.3 Refactor Phase — Clean Up

```
10. Clean up: remove duplication, improve names, extract helpers
11. Run ALL tests → confirm nothing broke
12. Git commit: "refactor: [feature id] — cleanup" (only if changes made)
```

### 4.4 TDD Rules

| Rule | Rationale |
|------|-----------|
| Must see a failing test before writing implementation | Prevents tests that always pass |
| `cargo test` must pass before marking feature as `passes: true` | Prevents premature completion |
| If test already exists from previous session, skip RED | Feature may be partially done |
| Refactor commits are optional | Only refactor if code actually needs cleanup |
| Regression tests must pass before new work | Catches breakage early |

## 5. Evaluator Agent

Spawned as a general-purpose subagent (via the Agent tool) at phase gates. The evaluator needs access to Bash (for `cargo test`), Playwright MCP (for visual verification), and Read/Grep (for code review).

### 5.1 Grading Criteria

| Criterion | Weight | Description |
|-----------|--------|-------------|
| Feature completeness | 40% | Every feature in feature-list.json passes. No stubs. Evaluator re-runs tests independently. |
| Correctness | 30% | No obvious bugs. Edge cases handled. Error paths don't crash. `cargo test` passes clean. |
| Code quality | 20% | Follows existing patterns. No security issues. Reasonable abstractions. No dead code. |
| PRD alignment | 10% | Implementation matches PRD intent, not just the letter of the feature description. |

### 5.2 Evaluator Process

```
1. Read phase-N/feature-list.json
2. Run cargo test → verify no failures
3. For each "visual" feature: Playwright screenshot, verify
4. For each "unit" feature: check test exists and passes
5. Read key source files → check code quality
6. Cross-reference with doc/PRD.md Phase N section
7. Write phase-N/phase-eval-report.md with:
   - Per-criterion score (0-10)
   - List of issues found (if any)
   - Pass/fail verdict (any criterion < 7 = fail)
8. Return verdict to main skill
```

### 5.3 Failure Handling

If evaluator fails the phase:
- Issues are added to feature-list.json as new entries with `"passes": false`
- Coder fixes them in next session (Branch B)
- Re-evaluate after fixes

| **Key deps** | All phases complete, `tray-icon` crate, Tauri bundler |
| **Phase gate** | App installs on Win+Mac, tray works, <50MB RAM idle, works offline |

## 7. Cross-Cutting Concerns

### 7.1 Phase Transition Protocol

Between every phase:
1. Evaluator runs full review on completed phase
2. `cargo test` full suite — no regressions from Phase 1 through current
3. Progress report written to `ditto-progress.json`
4. User shown phase summary and asked to confirm proceeding

### 7.2 Error Recovery

| Scenario | Recovery |
|----------|----------|
| `cargo test` fails at session start | Fix existing failures before implementing new features |
| LLM API unavailable during Phase 3 | Fall back to mock-based testing |
| Playwright MCP unavailable | `visual` tests degrade to `manual` with screenshot instruction |
| Evaluator rejects phase | Issues added as new features, coder fixes, re-evaluate |
| Context window fills mid-feature | Session ends cleanly; next session picks up from progress file |

### 7.3 Harness Invariants

| Invariant | Why |
|-----------|-----|
| Never modify feature descriptions or remove features | Prevents scope erosion |
| Only change `passes: false → true` after verified test | Prevents premature completion |
| Always run existing passing tests before new work | Catches regressions early |
| One feature per session is acceptable | Incremental > one-shot |
| Leave codebase in clean state at session end | Next session starts from known-good state |
| Phase gates require evaluator approval | External quality check prevents self-grading bias |

## 8. Skill Definition

### 8.1 Frontmatter

```yaml
name: ditto-implement
description: >-
  Long-running harness for implementing the Ditto desktop pet PRD.
  Drives TDD-based, phase-by-phase implementation with initializer,
  coder, and evaluator agents. Reads doc/PRD.md and ditto-harness/
  to determine current state and continue work.
```

### 8.2 Invocation

User types `/ditto-implement`. The skill:
1. Reads `ditto-harness/ditto-progress.json` to determine state
2. Follows the appropriate branch (A/B/C) from Section 3
3. Ends by updating progress and reporting status

### 8.3 Sections

1. **State Detection** — read progress, determine branch
2. **Initializer Logic** — generate phase artifacts from PRD
3. **Coder Logic** — TDD cycle per feature (Section 4)
4. **Evaluator Logic** — grading criteria and evaluation (Section 5)
5. **Session Handoff** — clean state protocol
6. **Phase Reference** — per-phase details (Section 6)
